## Question

[定移动机制](08-move-mechanic.md)给游戏加了「移动」。[模拟随机发牌的有解率与死局率](02-deal-simulation.md)的数据都是没有移动时测的，要在 [sim/](../sim/) 里把移动加进规则、求解器和模拟玩家，重新拿到下面这些数据：

1. **规则实现**：按[定移动机制](08-move-mechanic.md)的答案，写出列举一个局面所有"能配上的移动"的函数，配上手工用例（照 `test.mjs` 的写法）。至少覆盖这些情况：整串走、身后隔空位的牌不跟着走、停在中间某格、牌串里两张挨着的同牌不算配上、一张牌能配好几张、配不上就不算。
2. **随机发牌的有解率**：有了移动以后，随机发牌（不用赖子）有多少有解。还是几乎都无解的话，正推法照旧；如果变成大多有解，要说明。
3. **各档难度会不会卡住**：`spread` 取 0 / 0.25 / 0.5 / 0.75 / 1，让模拟玩家既会翻牌也会移动，统计遇到死局的比例、需要几个赖子才能通关，和 02 号报告的表格对照。
4. **求解器算移动要多久**：求解器要把移动算进分支，还要说明状态怎么去重（牌的位置会变，以前只看哪些格空了的哈希不够用）。在 Node 里测刚发好的牌阵和稳健型玩家翻到第 10 / 25 / 40 对时的耗时和超时率，看提示还能不能实时求解，并给出节点预算的建议。
5. **难度建议**：给出简单、普通、困难三档的 `spread` 建议值。如果最难一档加了移动以后也太简单，要说明，并给出可选的更难的发牌办法（不必实现）。

产物：脚本放在 `.scratch/fan-majiang/sim/`，结果报告写到 `.scratch/fan-majiang/research/09-move-simulation.md`，从本票链接过去。原型 `prototype/` 直接 import `sim/` 里的规则和求解器，改的时候别把原型现有的调用弄坏。

## Answer

**加了移动以后游戏容易了很多：随机发牌 97% 有解，最难一档也只相当于以前的普通。求解器算上移动仍然很快，提示可以实时求解；但"无解"要换一种方式证明。**

1. **规则实现**：[sim/move.mjs](../sim/move.mjs) 列举所有能配上的移动，同一次移动的几种配法归在一起；[sim/test-move.mjs](../sim/test-move.mjs) 有 24 个用例，覆盖票里列的六种情况，还和暴力实现在 3368 个随机局面上对照，结果完全一致。实现时注意到三点：
   - 串头前方挡路的那张是同牌时，停在哪一格都能配上；
   - 串尾身后隔着空位的同牌也算配上；
   - 只拖一张牌等于直接翻牌，求解器和死局判定只需要看两张以上的牌串。
2. **随机发牌的有解率**：1 万局里 97.2% 有解，2.8% 被证明无解（以前 2 万局只有 2 局有解）。筛选法（随机发牌、求解器确认有解才要）因此变得可行，平均 1.03 次发牌成一局。但随机发牌对玩家难得多：稳健型 82% 会卡住，平均要 2.9 个赖子。原因是正推法的牌阵只靠翻牌就能通关，随机发牌几乎一定要靠移动。所以简单和普通两档照旧用正推法。
3. **各档会不会卡住**：`spread` 取 0 / 0.25 / 0.5 / 0.75 / 1 时：
   - 稳健型遇到死局的比例是 1% / 2% / 3% / 6% / 15%（以前 5% / 9% / 16% / 29% / 56%）；
   - 随手型是 19% / 23% / 27% / 34% / 44%（以前 32%–87%）；
   - `spread = 1` 时，稳健型平均只要 0.2 个赖子。
   
   卡住时大多已经到了残局。中途局面几乎都仍然有解，只有 `spread = 1` 翻到第 55 对时降到 96%。
4. **求解耗时**：
   - **去重**：改用"每格放的是哪种牌"的 Zobrist 键。
   - **安全翻牌不再安全**：以前"只剩两张且能连上就先翻"的捷径，有移动时不成立。留着这一对，可以拿它当配对去移动所在的牌串，把别的牌顺路带走。复查 18 个"很可能无解"的局面，7 个其实有解。
   - **两轮搜索**：先用 10% 的预算走捷径快搜；没找到，再不走捷径地完整搜索，搜完才算证明无解。
   - **耗时**：Node 单线程中位数约 1 毫秒。预算 5 万节点时 P99 在 16 毫秒以内，最慢 67 毫秒，超时不到 0.5%。浏览器（桌面应用内置的 Chromium）和 Node 一样快。
   - **建议**：节点预算定为 5 万，超时兜底照旧保留。求解器找到的第一步有 20–38% 是一次移动，提示会经常给出移动。
   - **一处修正**：已定的兜底"沿生成解给下一对"，只在玩家还没移动过时成立。
5. **难度建议**：只用正推法的话，三档最多拉开到 1%–15%，**最难一档太简单**。
   - 更难的发牌办法（只测了数据，没有实现）：正推法发好后随机互换 k 对牌，再用求解器确认有解。几乎都一次成功，生成约 2 毫秒。k 从 0 到 68，稳健型卡住的比例从 15% 连续升到 77%，接近随机发牌。k ≥ 8 时几乎一定要用到移动才能通关。
   - 建议三档：简单 `spread = 0.75`（稳健型 6%）、普通 `spread = 1`（15%）、困难 `spread = 1` 再互换 16 对（51%），正好对上以前 5% / 16% / 56% 的拉开程度。
   - 自定义滑条可以分两段：前半段调 `spread`，后半段调互换对数。最终要试玩确认。

完整的数据表、方法和没有覆盖的部分见 [research/09-move-simulation.md](../research/09-move-simulation.md)。脚本在 [sim/](../sim/)；原型现有的调用不受影响（不传 `moves` 时行为不变），已经在浏览器里确认过。
